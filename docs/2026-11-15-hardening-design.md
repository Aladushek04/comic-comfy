# Устойчивость: срок хранения, атомарная запись, предел картинки, UTF-8

Дата: 2026-11-15. Решения согласованы в разговоре; числа и поведение заданы
пользователем, а не выбраны мной.

## Зачем

Четыре способа потерять работу или время, которые сегодня в коде открыты:

1. `webapp.service.JobService` держит задания и события в памяти без срока, а
   `out\jobs\` растёт с каждой загрузкой — за неделю работы панель и диск
   набирают мусор, который никто не убирает.
2. `write_cache`, `save_run` и запись пресета пишут JSON прямо в конечный файл:
   прерывание (Ctrl+C, полный диск, выключение) оставляет половину файла, и
   паспорт папки или кэш описания перестаёт читаться целиком.
3. `save_png` проверяет 30 МБ на входе, но не размер картинки: 30 МБ PNG
   спокойно бывает на 150 Мпикс, и такой файл занимает гигабайты RAM ещё до
   `thumbnail()`.
4. Отчёты и тесты падают при перенаправлении вывода: в пайп Python пишет в
   кодировке локали (здесь cp1252), и первый же `print` с кириллицей даёт
   `UnicodeEncodeError`. Команды из README без `PYTHONIOENCODING` не работают.

## Цели

- Память и диск панели не растут бесконечно: задания и черновики загрузок
  чистятся по сроку, **кадры и их `run.json` — никогда**.
- JSON (кэш описания, `run.json`, пресет) после обрыва либо прежний читаемый,
  либо новый целиком.
- Загрузка не может съесть RAM декодированием: отказ до декодирования, с
  числами в тексте ошибки.
- Проверки и CLI из README работают без переменных окружения, и в консоли,
  и через пайп.

## Не-цели

- Не чистим `out\<фото>_<хэш>\` (кадры, паспорт) и `out\presets\` — это
  результат работы пользователя.
- Нет фонового потока уборки и уборки при просмотре страницы: только при
  подъёме сервера и после постановки задания (решение пользователя).
- Не меняем формат кэша и паспорта — только способ записи.
- Не храним задания на диске для восстановления после перезапуска сервера:
  истёкшее задание — это сообщение в интерфейсе, а не восстановление.

## Чем это не должно стать (anti-goals)

- Удаление кадра или `run.json` ради места.
- Уборка задания, которое ещё в очереди или работает, и его исходника.
- Молчаливое уменьшение гигантской картинки вместо отказа.
- Сломанный вывод в `cmd` из-за смены кодировки: проверяем оба режима.

## Решения

### 1. Срок хранения (только `webapp/service.py`, `webapp/ui.py`, `webapp/state.py`)

- `JobService(workers=1, jobs_root=None, keep_hours=24.0, keep_jobs=30)`.
- `purge()` под `self._lock`:
  - задания со `status` `queued`/`running` не трогаются никогда;
  - завершённое задание остаётся в памяти, если оно моложе `keep_hours`
    **и** входит в последние `keep_jobs` завершённых; иначе удаляется из
    `_jobs` и `_order`;
  - `_latest` переезжает на последнее оставшееся;
  - после снятия блокировки удаляются папки `jobs_root\<id>` — только если имя
    папки совпадает с id и лежит внутри `jobs_root` (никаких `..`).
- `purge_uploads()`: папки `jobs_root\uploads\<uid>` старше `keep_hours`
  удаляются. Черновик **не** удаляется после «Старт»: `/media/upload/{uid}`
  показывает превью, пока задание идёт, и минимум сутки после.
- Вызовы: в `__init__` (подъём сервера) и в начале `submit()` (после
  постановки). Возвращает список снятых id — для проверок и лога.
- `?job=` на снятое задание: `webapp.state.missing_job_text(job_id)` даёт
  «История задания истекла: файлы кадров остались в `out\<фото>_<хэш>`», а без
  id — прежнее «Задание не запущено». `ui.refresh` берёт текст оттуда.
- `media_job` для снятого задания отвечает 404 — так уже работает.

### 2. Атомарная запись JSON (`tools/photo_prompt.py`, `tools/jobs.py`)

- `photo_prompt.write_json(path, data, indent=2)`: `json.dumps` → временный файл
  `path.name.*.tmp` в **той же папке** → `flush` + `os.fsync` → `os.replace`.
  При любом исключении временный файл удаляется, целевой не тронут.
  `os.replace` атомарен только в пределах одной файловой системы, поэтому
  временный файл кладётся рядом с целевым, а не в `%TEMP%`.
- Применяется в `write_cache`, `save_run` (запись `run.json` целиком, вместе с
  историей) и в записи пресета `jobs.py`.
- Ошибка записи (нет места, нет прав) по-прежнему всплывает: `save_run`
  возвращает `None` только когда кадра нет, а не когда не смог записать
  паспорт — иначе пропавший паспорт выглядел бы нормой.
- Существующий `run.json`, который не читается, — `PipelineError`: пустой паспорт
  вместо истории молча теряет записи о прежних кадрах. Читаем паспорт **до**
  копирования кадра, поэтому неудача не оставляет кадр без записи.

### 3. Предел картинки (`webapp/service.py`)

- `MAX_SIDE = 8192`, `MAX_PIXELS = 64 * 1024 * 1024` рядом с `MAX_UPLOAD`.
- Размер читается из заголовка **до** `Image.open` для PNG (обход чанков до
  IHDR) и JPEG (первый SOF): PIL не открывает кадр больше ~179 Мпикс и отвечает
  своей английской ошибкой без размеров, а `verify()` на обрезанном файле
  говорит «не картинка».
- Остальные форматы проверяются по `im.size` сразу после `Image.open` — и
  только потом `verify()`, `exif_transpose`, `convert`, `thumbnail(4096)`,
  `save`. `DecompressionBombError` переводится в тот же русский текст с
  пределами.
- Текст ошибки: «файл 12000×9000 (108.0 Мпикс) больше предела: сторона до
  8192 px, площадь до 64.0 Мпикс».

### 4. UTF-8 в точках входа (`tools/settings.py` и пять скриптов)

- `settings.utf8_streams()`: `sys.stdout` и `sys.stderr` →
  `reconfigure(encoding="utf-8", errors="replace")`, если ещё не UTF-8;
  идемпотентно, ничего не делает с подменёнными потоками без `reconfigure`.
  `errors="replace"` — чтобы падение было невозможно даже в чужом терминале.
- Вызов: `photo_prompt.py`, `build_workflows.py`, `check_install.py` — первой
  строкой в блоке `__main__`; `test_photo_prompt.py`, `test_web_app.py` — на
  уровне модуля (через импорт `test_web_app` это покрывает и `test_web_ui.py`).
- `webapp/run.py` в этом заходе не трогаем: он поднимается из `.cmd`/`.ps1` со
  своим окружением. Если понадобится — отдельная строка в плане.

## Подходы, которые не выбраны

- **Хранение на диске вместо памяти** (перечитывать `run.json` папок): дороже
  и не нужно — кадры и паспорт и так на диске, а задание живёт минуты.
- **Фоновый поток уборки**: мешает тестам, Ctrl+C и не даёт предсказуемого
  момента проверки. Уборка на двух событиях проверяется напрямую.
- **`errors="replace"` без смены кодировки**: не падает, но кириллица в логе
  превращается в `?` — теряется ровно то, ради чего лог читают.
- **Молчаливый `thumbnail` для гигантских файлов**: пользователь не узнает,
  что прислал не то фото, и получит кадр по уменьшённой копии.

## Как проверяется

- `test_web_app.py`: уборка памяти (срок и счётчик), неприкосновенность
  `queued`/`running`, удаление папки задания и сохранение кадров, черновик
  загрузки живёт сутки, текст для истёкшего `?job=`, отказ по стороне и по
  площади (с числами в тексте), отсутствие декодирования при отказе.
- `test_photo_prompt.py`: обрыв записи кэша, `run.json` и пресета оставляет
  прежний JSON читаемым и не оставляет `.tmp`; `write_json` не теряет старый
  файл при `fsync`-ошибке; запуск CLI и тестов **через пайп без
  `PYTHONIOENCODING`** даёт читаемую кириллицу и код 0/1, а не трейсбек.
- `test_web_ui.py`: страница с `?job=` на неизвестное задание показывает текст
  об истёкшей истории.
- `AGENTS.md` и README: новые числа проверок и правила (что чистится, что нет).
